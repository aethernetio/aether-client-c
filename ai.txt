
AETHER C CLIENT — ARCHITECTURE CONTEXT FOR AI
=============================================

Purpose of this file
--------------------

This file is the compact architectural context that should be supplied to an AI before it changes this repository.

It is intentionally NOT:
- a development diary;
- a task specification;
- a list of old bugs;
- a transcript of previous AI work;
- a changelog.

Keep it current when the architecture changes. Prefer durable design facts, invariants, file locations, ownership rules, regeneration commands, and validation requirements.

Repository purpose
------------------

This repository contains the C implementation of the Aether client.

The runtime is designed for small systems, including MCUs. The core library is intentionally usable without a heap. Application-owned storage, fixed client state, caller-provided protocol buffers, and platform callbacks are preferred over hidden allocation.

The repository also contains a C ADSL compiler/generator used to produce protocol bindings from the same ADSL schemas used by the other Aether implementations.

Primary design goals
--------------------

1. Small linked firmware footprint.
2. No mandatory heap allocation in the client runtime.
3. Explicit ownership and lifetime.
4. Platform independence.
5. Protocol compatibility with the Java/TypeScript Aether implementations.
6. Generated protocol code must come from ADSL, not from manually duplicated API definitions.
7. Generated code size is evaluated by linked firmware size, not by source size or static-library/object size.
8. Common serialization code is shared only where sharing actually reduces linked size.
9. `-ffunction-sections -fdata-sections` plus linker garbage collection is an important part of the size model.

Top-level architecture
----------------------

The code can be understood as five layers:

1. Public client/runtime API
   - `include/aether_client.h`
   - `src/aether_client.c`

2. Application and asynchronous helpers
   - `include/aether_client_app.h`
   - `include/aether_rx.h`
   - `include/aether_send_future.h`
   - matching `src/*.c` files

3. Platform/transport boundary
   - `include/aether_platform.h`
   - platform implementations such as the ESP32 port

4. Protocol and registration bindings
   - production generated code under `src/generated/`
   - shared wire primitives in:
     - `include/aether_meta_runtime.h`
     - `src/aether_meta_runtime.c`

5. ADSL compiler/generator
   - `tools/aether-protocol-c/`
   - parser/model: `src/adsl.c`
   - emitter: `src/emitter.c`
   - CLI: `src/main.c`
   - public generator interface: `include/adslc.h`
   - generator regression tests: `tests/`

Public client object and ownership
----------------------------------

`aether_client_t` is the central runtime state object.

Important ownership rule:
- the caller owns the `aether_client_t` storage;
- the client does not require dynamic allocation for its normal runtime state;
- pointers passed as configuration/storage must remain valid for the documented lifetime;
- transport/platform state is provided through explicit platform integration rather than hidden process-global allocation.

Current measured `sizeof(aether_client_t)`:
- 4432 bytes on the current host build.

Do not casually add large arrays or platform-specific state to `aether_client_t`. MCU RAM footprint is a first-class constraint.

Client lifecycle
----------------

The main lifecycle is implemented in `src/aether_client.c`.

The important public/runtime stages are:

1. Initialize client state.
2. Start the client/transport.
3. Drive progress by polling and by transport callbacks.
4. Receive transport state changes through the client transport-state entry point.
5. Feed received bytes into the RX path.
6. Run registration when persistent registration state is unavailable or invalid.
7. Enter the authorized state.
8. Send/receive application messages.
9. Stop/tear down without assuming heap ownership.

The implementation is event/state driven. Do not introduce blocking protocol loops into the core client.

Transport callbacks and polling can interact with the same state machine. When changing transitions, reason about:
- whether a callback may arrive immediately;
- whether an operation can complete synchronously;
- whether state is committed before invoking code that may re-enter the client;
- whether a timeout/retry path can see partially updated state.

RX architecture
---------------

RX code is split from the main client so different receive strategies can be linked independently.

Relevant files include:
- `include/aether_rx.h`
- `src/aether_rx_first.c`
- `src/aether_rx_all.c`
- `src/aether_rx_adaptive.c`

`aether_client_on_rx()` is the important ingress point from the transport side.

Do not assume that an incoming transport chunk is exactly one logical protocol message unless the specific transport contract guarantees that. Preserve the existing framing/ingress semantics.

Send/future architecture
------------------------

Asynchronous send tracking is implemented with the send-future layer:
- `include/aether_send_future.h`
- `src/aether_send_future.c`

The client supports both fire-and-forget style paths and paths that wait for a protocol result.

Keep result/request identifiers and completion ownership explicit. Avoid allocating a future object per request on the heap.

Platform boundary
-----------------

`include/aether_platform.h` defines the platform-facing contract.

Platform-specific code owns details such as:
- transport creation and connection;
- clocks/timers;
- random/entropy integration where required;
- platform context;
- network I/O.

The core client must not include ESP-IDF/POSIX-specific behavior directly.

For MCU work, platform context is caller/fixed-storage oriented. Do not replace this with implicit heap state.

Registration architecture
-------------------------


Registration is a multi-stage protocol flow. The low-level client coordinates small registration adapter/build-helper modules with protocol bindings emitted from ADSL.

Conceptually the registration flow crosses different trust/protocol phases:

Generated binding policy
------------------------

Only the direct ADSL compiler outputs described above are generator-owned outputs.

Rule:
DO NOT hand-edit `client_server_*` generated protocol files as the primary fix.

If direct generated output is wrong:
1. change `tools/aether-protocol-c/src/emitter.c` or parser/model code;
2. add/update a focused generator fixture/test;
3. rebuild the generator;

Wire runtime
------------

Shared serialization primitives:
- `include/aether_meta_runtime.h`
- `src/aether_meta_runtime.c`

Writer design:
- writers are out-of-line shared functions;
- generated call sites pass:
  - destination buffer;
  - capacity;
  - cursor/position;
  - value;
- no heap allocation is required;
- writers return `aether_status_t`.

The shared writer runtime is intentionally out-of-line because production generated code has many call sites and sharing reduces linked flash size.

Current production generated writer usage is substantial:
- UUID: 15 call sites;
- pack: 14;
- bytes: 14;
- u16: 12;
- u64: 9;
- u8: 7;
- u32: 7.

Reader design:
- `aether_meta_reader_t` is `{ data, length, position }`;
- reader primitives are handwritten `static inline` functions in `aether_meta_runtime.h`;
- this is deliberate.

The registrationDirect response is currently the production consumer of these reader primitives. Keeping them header-inline lets `-Os` inline the profitable parts without requiring LTO while still maintaining one handwritten source of truth.

Do not move readers back to per-generated-file copy/paste helpers.

Current ESP32 output leaves only a small local `aether_meta_read_u16le` helper after optimization; the compiler inlines the rest where profitable. Do not force `always_inline` without measuring.

Integer and byte ordering
-------------------------

Wire compatibility is more important than C-native representation.

Current important rules:
- integer primitives emitted by the shared runtime use explicit little-endian wire order;
- UUID serialization preserves the Aether UUID wire representation: MSB and LSB halves are emitted bytewise in their required order rather than memcpy-ing a host struct;
- variable-length byte/string data is length-prefixed through the Aether pack encoding;
- never serialize C struct memory directly.

Intpack
-------

The generator/runtime implements Aether's compact integer packing format.

Do not substitute LEB128, protobuf varint, or a platform-native encoding.

Both encode and decode changes require exact boundary-value tests.

Polymorphic/hierarchy types
----------------------------

ADSL inheritance/hierarchy values are represented through generated reference/tagged-union style C types.

The important optimization rule is selective sharing:

- polymorphic hierarchy parameters such as `Key` use reusable generated serializers in `<base>_types.c`;
- ordinary single-use concrete structs are currently serialized inline at API call sites;
- concrete serializers can still be generated in types files and removed by linker GC when unused.

This policy is measurement-driven.

For the production registration API:
- `setReturnKey` uses the shared Key serializer;
- `registrationDirect` uses the same shared Key serializer;
- only `client_server_reg_safe_serialize_key` survives in the linked ESP32 firmware from the generated serializer set.

Do not blindly convert every concrete struct call site to an out-of-line serializer. A measured experiment increased firmware size for single-use `Cloud`.

Linker garbage collection
-------------------------

The design assumes:
- `-ffunction-sections`
- `-fdata-sections`
- linker section garbage collection

Therefore:
- the size of `client_server_reg_safe_types.c.o` is NOT the firmware cost;
- the number of generated functions is NOT the firmware cost;
- linked ELF/firmware measurements are authoritative.

Always distinguish:
1. source size;
2. object/archive size;
3. linked ELF text/data/bss;
4. final firmware image size.

No-heap rule
------------

The runtime must remain usable without heap allocation.

Preferred patterns:
- caller-owned structs;
- caller-owned buffers;
- fixed-size arrays where bounded by protocol/configuration;
- views (`pointer + length`);
- explicit storage passed into response decoding;
- stack-local temporary state where bounded.

Do not introduce malloc/calloc/realloc/free into the core client or generated protocol runtime without an explicit architectural decision.

Crypto boundary
---------------

The client uses bundled crypto implementations/backends, including Hydrogen and the configured asymmetric backend.

Crypto code is a significant part of generic object size, but object size is not equal to linked MCU footprint.

Do not duplicate cryptographic primitives inside generated protocol code.

Protocol code should serialize/transport keys; cryptographic operations remain behind the crypto/backend boundary.

Application wrapper
-------------------

`aether_client_app` is a convenience/application layer around the lower-level client.

Keep the low-level client usable without the app wrapper. Do not move fundamental transport/protocol ownership into the convenience layer.

Current architectural conclusion
--------------------------------

The current measured size policy is intentionally hybrid:

- shared out-of-line writer primitives;
- shared out-of-line polymorphic Key serializer where reuse exists;
- inline serialization for single-use concrete API structures;
- generated concrete serializers remain available and are linker-GC-friendly;
- shared handwritten header-inline reader primitives;
- no mandatory heap allocation.

This is not accidental inconsistency. It is the result of linked-size measurements on the actual ESP32 production path.

When changing this policy, provide a linked A/B measurement and keep functional/wire tests green.

[C client architecture: optional registration]
Registration is not part of the mandatory client state machine. The mandatory client owns an existing identity (UID + masterKey), work-server cache/discovery, work connection/auth, ping/UAP and messaging. Missing identity is a normal NO_IDENTITY state; core must not automatically register. Missing/exhausted work servers is a normal client state only after identity exists: core connects to registration/bootstrap service and calls resolveServers, authenticated with the existing masterKey, refreshes the server cache, then resumes work connection. Self-registration is a separate caller-owned optional component, scheduled explicitly by the application when desired. It obtains UID + masterKey and installs that identity into the client. Provisioned firmware can omit the registration component entirely.

[C client server-resolution protocol finding]
Canonical protocol inspection corrected an earlier assumption: ClientApiRegUnsafe.enterGlobal / GlobalRegServerApi.finish are legacy/new-client registration machinery, not existing-identity recovery. Current Java ConnectionRegistration explicitly treats enterGlobal as legacy compatibility and registrationDirect does not open GlobalApi. GlobalRegServerApiImpl.finish creates a new random UID and alias, so it must never be used to restore an existing identity. ServerRegistrationApi.resolveServers(Cloud) is independent and only resolves ServerDescriptor[] for an already-known Cloud. Therefore mandatory C client SERVER_RESOLVING must use the ordinary registration safe stream with a fresh temporary return key and call resolveServers(existing cloud_sids), with no PoW and no masterKey registration transaction. Current protocol cannot reconstruct Cloud from UID+masterKey alone; Java persists Cloud separately from ServerDescriptor[] as client routing state. To support provisioning from strictly UID+masterKey with no Cloud would require a separate server protocol/API addition. For the current refactor, Cloud remains persistent routing identity metadata while ServerDescriptor[] is disposable cache.
[C client optional-registration extraction checkpoint] Registration RAM/state ownership and link reachability were split from mandatory core. aether_client_t shrank from 4432 to 4016 bytes (-416 bytes per client); optional aether_registration_t owns PoW/direct-registration state and its internal event callbacks. Mandatory SERVER_RESOLVING has an independent RX path and keeps only bootstrap requirements (registration server signed key, temp return key, Cloud, req_server_key/req_resolve, descriptor cache). aether_client_poll/on_transport_state/on_rx route REG_* self-registration through caller-owned component callbacks, while SERVER_RESOLVING remains direct mandatory core behavior. Provisioned ESP32 thermometer must be checked by linked ELF symbols/flash: archive/object sizes are not flash footprint.
[C client SERVER_RESOLVING availability semantics] Once identity + Cloud exist, bootstrap/work-server unavailability is normal retryable client state, not terminal ERROR. begin_server_resolving keeps AETHER_STATE_SERVER_RESOLVING and returns AETHER_OK when registration/bootstrap transport_open fails; poll retries after operation_timeout_ms. Registration-channel transport_send failures for getServerKey and encrypted resolveServers likewise close the transient transport, keep SERVER_RESOLVING, reset the retry anchor, and emit no ERROR event. send_resolve_servers enters SERVER_RESOLVING before attempting the transport send, so the first descriptor-resolution send immediately after registrationDirect is already governed by mandatory resolver semantics. Protocol/crypto/trust/storage failures remain terminal. Regressions cover: registrationDirect identity persistence despite failed first resolveServers send, persisted-identity startup with unavailable bootstrap endpoint, and failed getServerKey send followed by poll retry.
[C client identity producers] Mandatory core now exposes aether_client_provision_identity(client, uid, alias, master_key, cloud_sids, cloud_count) as the non-registration identity producer. It is valid only in AETHER_STATE_NO_IDENTITY, requires a non-empty Cloud and no registration component/PoW callback, clears ServerDescriptor[] as disposable cache, persists identity + Cloud through the ordinary save_state format, emits REGISTERED, then enters mandatory SERVER_RESOLVING. Optional aether_registration_t remains the second caller-owned producer of the same identity. Current protocol provisioning requires UID + alias + masterKey + Cloud; UID + masterKey alone cannot reconstruct Cloud. Provisioned identity survives restart through the same persistence format and resumes descriptor resolution without self-registration.
[C client zero-incremental-RAM registration bridge] The optional registration bridge pointer no longer has dedicated storage in aether_client_t. It aliases the mandatory ServerDescriptor[] cache through an anonymous union: during NO_IDENTITY/REG_* the descriptor cache is unused and may hold the caller-owned aether_registration_t pointer; after registrationDirect identity creation the client enters SERVER_RESOLVING, registration callbacks are no longer dispatched, and descriptor resolution reclaims the same bytes as servers[]. This preserves existing platform RX/transport routing without adding registration RAM to provisioned clients and without making optional registration symbols reachable in the provisioned linked ELF. aether_registration_init binds the overlay only for an unregistered client with an empty descriptor cache.
[C client registration dispatch compaction] Optional registration dispatch uses one immutable internal ops-table pointer per aether_registration_t instead of three per-instance callback pointers. The static ops table owns the relocations to registration RX/transport/poll handlers, so mandatory aether_client.c still dispatches indirectly and provisioned firmware does not make optional registration code reachable. This reduces caller-owned optional registration RAM while preserving the ServerDescriptor[] overlay that gives the mandatory provisioned core zero incremental registration-bridge RAM.
[C client optional-registration final ownership] aether_registration_t no longer contains the write-only `started` flag; registration progress is represented solely by the client REG_* state machine and aether_registration_done() derives completion from the installed identity. The self-registration wire/parser implementation intentionally remains physically in aether_client.c behind the narrow internal bridge: moving it to aether_registration.c would require exposing numerous core-only transport/error/crypto/storage/reader helpers while providing no mandatory RAM or provisioned linked-flash benefit. Function-section GC already removes this optional implementation from provisioned firmware, so preserving the smaller private API is the stronger abstraction boundary.
[C client footprint measurement: Hydrogen correction] Do not report ESP-IDF `spiffs/spiffs/src/spiffs_hydrogen.c.o` as Aether bundled libhydrogen; it is unrelated SPIFFS code. For MCU footprint reports, bundled Hydrogen has two distinct measurements: (1) optimized `.text/.data/.bss` from the actual `aether_hydrogen_vendor` Release target/object(s), which is an object-level diagnostic and not automatically equal to firmware flash; and (2) actual linked contribution in the target firmware, determined from ELF symbols/linker map. The ESP32-C3 provisioned thermometer currently contains zero `hydro_*` symbols, so bundled libhydrogen linked contribution in that firmware is 0 bytes. Always distinguish archive/object file size, section sizes, and actual linked firmware footprint.
[C client messaging architecture] Messaging has two independent public levels sharing the same core TX primitive. `aether_send_message(client, destination, data, size)` is the minimal one-way immediate/zero-extra-state operation; readiness/writability is validated internally, so callers do not need an `aether_is_ready()` guard. The optional bidirectional layer is a single caller-owned `aether_peer_t`: `aether_peer_init(peer, client, remote_uid)`, `aether_peer_on_message(peer, callback, ctx)`, `aether_peer_send(peer, data, size)`. There is no public router object and no peer/router storage or dispatch branch in mandatory `aether_t`. `aether_messages.c` owns only a tiny optional intrusive registry keyed by `(client, uid)` and is absent from non-peer firmware. The base peer has no heap, queue, copied payload storage, retry policy or configuration arrays. Advanced buffering/replacement/retry policy belongs in a separate optional component rather than expanding the default API.
[C client thermometer bidirectional example] ESP32 thermometer now demonstrates the default optional bidirectional channel rather than global receive-all routing. Application code owns one `aether_peer_t server_peer`, binds it once with `aether_peer_init(&server_peer, &client, server_uid)`, and installs `aether_peer_on_message(&server_peer, on_server_message, NULL)`. The remote UID is configured as two compile-time 64-bit halves to avoid a UUID string parser/heap/config subsystem on MCU. The example explicitly compiles `aether_messages.c`; applications using only `aether_send_message()` do not. `aether_is_ready()` is not required for messaging and remains in the thermometer only as a diagnostic status value. The example currently has no real temperature sensor driver or telemetry wire contract, so no invented sensor payload/send loop was added.
[C client bidirectional peer measured MCU footprint] Correct reachable-path ESP32-C3 measurement uses a temporary non-zero compile-time remote UID so -Os/LTO cannot eliminate the peer/start path. Zero-peer provisioned thermometer baseline: RAM 21556 B, app flash 417068 B, firmware.bin 430512 B, linked ELF text=410184/data=7432/bss=384732. Reachable bidirectional peer build: RAM 21596 B (+40 B), app flash 417624 B (+556 B reported app flash), firmware.bin 431040 B (+528 B), linked ELF text=410740 (+556), data=7432 (unchanged), bss=384780 (+48). ESP32-C3 ABI `sizeof(aether_peer_t)` is 32 B; linked `server_peer` symbol is 32 B and optional registry head `peers` is 4 B. `aether_messages.c.o` diagnostic sections are text=696/data=0/bss=4, but object size is not actual linked firmware footprint. Linked bundled Hydrogen remains 0 B. The ignored local thermometer_secrets.h was restored to UID {0,0} after measurement.

C client mandatory recovery architecture: (1) Recovery is a mandatory core reliability mechanism, not a caller-owned component. It uses ServerRegistrationApi.recovery(uid, masterKey) via the existing aether_generated_reg_safe_build_recovery adapter; no hand-coded method id or Key serialization. Recovery response alias + Cloud + ServerDescriptor[] is parsed by the existing parse_server_array/parse_server_descriptor; no second descriptor parser. (2) aether_set_credentials(client, uid, master_key) is a one-time idempotent identity provisioning API (no aether_credentials_t component, no poll/callbacks/internal ops). If credentials already exist it returns AETHER_OK without overwriting UID/masterKey, so a repeated startup call cannot roll back a rotated key. load_state() priority: persisted identity always wins over a caller candidate supplied before start. (3) Topology escalation: cached descriptors are tried first; resolveServers(known Cloud) is a single cheap refresh; if the refreshed topology is still unusable the flag topology_refreshed=true (set only on a resolveServers RESPONSE) drives escalation to authoritative recovery instead of looping on the stale Cloud. topology_refreshed resets on successful WORK connection and after recovery. (4) Recovery never changes UID/masterKey; it only updates alias/Cloud/descriptors and persists via save_state; it never emits AETHER_EVENT_REGISTERED. (5) Recovery bootstrap/send/transport failures are retryable SERVER/RECOVERY states, not terminal ERROR. Recovery states: AETHER_STATE_RECOVERY_CONNECTING / _WAIT_SERVER_KEY / _WAIT_RESULT. sizeof(aether_client_t) preserved at 4008 bytes.
C client recovery transaction semantics: recovery RESULT commit is atomic w.r.t. persistence. The RESULT branch sets registered=true only as a commit marker, calls save_state(), and on storage failure rolls the marker back to false before entering ERROR. This guarantees: (1) an initial recovery after aether_set_credentials() does not leave registered=true when flash save fails; (2) an already-registered client whose recovery refresh fails persistence is not left in a partially committed state. aether_client_retry() from ERROR re-runs authoritative recovery when caller/persisted credentials are present instead of jumping directly to WORK. Regression test_recovery_save_failure_is_not_committed covers: caller credentials -> recovery -> successful response -> save fails -> ERROR/AETHER_ERR_STORAGE -> UID/masterKey preserved -> registered==false -> retry re-enters RECOVERY_CONNECTING.
C client REGISTERED event scope: recovery never emits AETHER_EVENT_REGISTERED. REGISTERED is a genuine registration event where the server creates a new identity; recovery only proves an existing uid+masterKey and restores routing (alias/Cloud/descriptors). This holds both for initial aether_set_credentials() provisioning and for an already-registered client topology refresh. The recovery RESULT branch no longer computes first_identity and never emits REGISTERED.
