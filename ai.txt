
AETHER C CLIENT — ARCHITECTURE CONTEXT FOR AI
=============================================

Purpose of this file
--------------------
Compact, durable architectural context for the C Aether client. Supply to an AI before it changes this repository.
This file is intentionally NOT a development diary, changelog, task log, bug list, or AI transcript. Do not append chronological history. Replace obsolete facts in place.

Repository purpose
------------------
C implementation of the Aether client plus a C ADSL generator/compiler (`tools/aether-protocol-c`) that emits protocol bindings from the same ADSL schemas used by Java/TypeScript.
Runtime targets small systems, including MCUs. Core library is usable without heap.

Primary design goals
--------------------
1. Small linked firmware footprint.
2. No mandatory heap allocation in the client runtime.
3. Explicit ownership and lifetime.
4. Platform independence.
5. Protocol compatibility with the Java/TypeScript Aether implementations.
6. Generated protocol code comes from ADSL; do not hand-duplicate API definitions.
7. Generated code size is judged by linked firmware size, not object/archive/source size.
8. `-ffunction-sections -fdata-sections` + linker GC is part of the size model.

Top-level source layout
-----------------------
The code has these layers:
1. Beginner facade
   - `include/aether.h`, `src/aether.c`
2. Advanced application wrapper and async helpers
   - `include/aether_client_app.h`, `include/aether_rx.h`, `include/aether_send_future.h`, `include/aether_transport.h`, `include/aether_transport_server.h`
3. Low-level client core
   - `include/aether_client.h`, `src/aether_client.c`
4. Optional caller-owned components
   - `include/aether_registration.h` (self-registration)
   - `include/aether_messages.h` (aether_peer_t bidirectional channel)
   - `include/aether_lan.h` (LAN discovery + direct delivery)
5. Platform/transport boundary
   - `include/aether_platform.h`
   - `platform/posix/`, `platform/esp32/`

6. Crypto boundary and registry
   - `include/aether_crypto_registry.h`, `src/aether_crypto_registry.c` — generic registry, in build
   - `include/aether_hydrogen.h`, `src/aether_hydrogen.c` — Hydrogen provider (test support; not in aether_client by default)
   - `platform/esp32/aether_crypto_p256_aes_gcm.c` — P256/AES-GCM provider, ESP32 only


7. Wire runtime and data I/O
   - `include/aether_meta_runtime.h`, `src/aether_meta_runtime.c` — in build
   - `include/aether_dataio.h`, `src/aether_dataio.c` — present but NOT in aether_client build (peer path disabled)

8. Generated protocol bindings and maintained registration adapters
   - `src/generated/` (see naming warning below)
9. ADSL compiler/generator
   - `tools/aether-protocol-c/`
   - parser/model: `src/adsl.c`
   - emitter: `src/emitter.c`
   - CLI: `src/main.c`
   - public generator API: `include/adslc.h`

Beginner facade and component model
------------------------------------
`aether_t` is the beginner-facing caller-owned object. It contains:
- `aether_client_app_t app` — mandatory protocol/application state, including `core` and the semantic transport (`aether_transport_t`) plus server transport (`aether_transport_server_t`)
- `aether_rx_all_t rx` — receive-all policy
- `aether_message_fn on_message`, `aether_ready_fn on_ready`, `aether_error_fn on_error`
- `platform_context` opaque byte storage for the platform package
- caller-owned component registry: `aether_component_t *components`, `size_t component_capacity`, `size_t component_count`

Unified component registry
--------------------------
A component is `{ void *context; aether_component_work_fn work; }`. Caller-owned storage; no heap, no hidden dynamic list, no fixed global max. `AETHER_COMPONENT_CAPACITY_DEFAULT` is only a recommendation.
`aether_set_components()` must be called before `aether_start()`; after start returns `AETHER_ERR_STATE`. Replacing the registry pre-start resets count. Duplicate exact `(context, work)` is rejected with `AETHER_ERR_STATE`.
`aether_work()` order: (1) one core mechanism step; (2) `AETHER_ERR_ARGUMENT`/`AETHER_ERR_STATE` from core -> immediate return, no component ticks; (3) one bounded pass of all components; (4) exactly one transport flush if BUILDING; (5) exactly one transport tick; (6) no second flush.
Component count is snapshotted at pass start; components registered during a tick become active on the next `aether_work()`. Every component gets one tick per call. Waiting for a prerequisite is normal `AETHER_OK`; there is no "retry next tick" status. First non-OK component status is remembered and returned after the pass; core non-OK status takes precedence.
Registration component special case: `aether_registration_init(&registration, &aether.app.core)` must run AFTER `aether_start()`, because `aether_start()` reinitialises the core. Then `aether_register_component(&aether, &registration, aether_registration_work)`.

Messaging
---------
Two independent levels share the same core TX primitive:
- `aether_send_message(client, destination, data, size)` — minimal one-way immediate operation; internally checks readiness/writability; payload borrowed for the call only.
- `include/aether_messages.h` optional bidirectional layer: caller-owned `aether_peer_t`. API: `aether_peer_init(peer, client, uid)`, `aether_peer_on_message(peer, cb, ctx)`, `aether_peer_send(peer, data, size)`, `aether_peer_close(peer)`, `aether_peer_uid(peer)`.
`src/aether_messages.c` owns a tiny optional intrusive registry keyed by `(client, uid)`, absent from non-peer firmware. Base peer has no heap, queue, copied payload storage, retry policy or configuration arrays. Advanced buffering belongs in a separate optional component.
`aether_send_message` maps to `aether_client_app_send` -> `aether_client_send_message`. That core path is the same underlying primitive used by the semantic transport.

Shared ingress helper
---------------------
`src/aether_internal.c` exports `aether_dispatch_message_internal(client, from, payload, length)`. It is the single user-callback dispatch point:
- guards NULL client / NULL payload with length>0 -> `AETHER_ERR_ARGUMENT`
- no `on_message` -> `AETHER_OK`
- sets `core.callback_active` around the user callback and restores previous value
- used by the cloud/beginner RX path and by the LAN component
Do not call `on_message` directly. Do not add a second dispatch path.

Client lifecycle and states
---------------------------
Important public/runtime stages:
1. Initialize client state and install callbacks/components.
2. `aether_start()` — restore identity / start mandatory recovery or registration, start network.
3. Drive progress with `aether_work()` and transport callbacks.
4. Feed received bytes through `aether_client_on_rx()` / platform RX integration.
5. Mandatory recovery when routing state is missing or stale.
6. Authorized/READY messaging.
7. `aether_stop()` — stop protocol/network, reset transport, release platform resources.
The implementation is event/state driven. Do not introduce blocking protocol loops into the core client.

Identity, credentials and mandatory recovery
---------------------------------------------
`include/aether_credentials.h`:
- `aether_set_credentials(client, uid, master_key[32])` — one-shot, idempotent; does not overwrite existing identity.
- `aether_set_credentials_typed(client, uid, master_key[32], master_key_type)` — same but with an explicit wire key type.
Persisted state version 3 stores `recovery_key_pending` plus `pending_recovery_key` plus `master_key_type`, backward-compatible with v1/v2. A valid pending transition is loaded even when `registered=false`, and startup resumes RECOVERY instead of WORK.
Recovery is mandatory core reliability, not a caller-owned component. It uses `ServerRegistrationApi.recovery(uid, oldMasterKey, newMasterKey)` through the generated safe-registration adapter; do not hand-code method id or key serialization.
Cross-provider rotation contract: old key authenticated by raw bytes constant-time against stored identity; new key constructed with the active backend provider; old key wire type is tracked in `master_key_type` and serialized for the old key; active backend type used for new/return keys. `master_key_type` rotates atomically with the key bytes; rollback restores it.
Recovery is crash-consistent: keep old key authoritative while the request is in flight; generate and persist pending new key before first request; on success promote pending before `save_state()`; on commit-save failure restore old key + keep the same pending key for retry; clear pending only after durable success.
Recovery never emits `AETHER_EVENT_REGISTERED`; it only restores routing. `REGISTERED` is a genuine new-identity event from registration.
Recovery bootstrap/send/transport failures are retryable `RECOVERY_*` states, not terminal ERROR. `aether_client_retry()` prioritises `recovery_key_pending` over `registered`.

Optional self-registration
--------------------------
`include/aether_registration.h` + `src/aether_registration.c` is a caller-owned optional component. Not part of the mandatory state machine. `aether_registration_work()` is the component adapter; normalises transient `AETHER_ERR_BUSY` to `AETHER_OK`. Provisioned firmware can omit it entirely.

RX architecture
---------------
RX code is split from the main client so strategies can be linked independently:
- `include/aether_rx.h`, `src/aether_rx_first.c`, `src/aether_rx_all.c`, `src/aether_rx_adaptive.c`
`aether_client_on_rx()` is the transport-side ingress. An incoming transport chunk is not assumed to be exactly one logical message.
The beginner `aether_t` owns an `aether_rx_all_t rx` receive-all policy. Lower API levels keep this outside the core.

Semantic transport
------------------
`include/aether_transport.h` defines the upper-layer semantic transport (`aether_transport_t` = `{ ctx, vtable }`, `aether_transport_status_t`, `aether_transport_listener_t`). Batch states include BUILDING/FLUSHING. `aether_transport_send_message` queues; `aether_work()` owns batch boundaries (one flush + one tick per pass).
`include/aether_transport_server.h` implements a concrete server transport (`aether_transport_server_t`) with typed inline command storage (MAX=4). `aether_transport_server_init(server, app)` takes only the server and the app; the caller does not supply batch storage. `aether_transport_server_bind(transport, server)` binds it.
The low-level raw I/O vtable is `aether_transport_io_vtable_t`, exposed in `aether_client_config_t` and `aether_client_app_config_t` as `transport_io`. Do not confuse it with the semantic transport.

Platform boundary
------------------
`include/aether_platform.h` defines the platform contract: transport creation/connection, clocks/timers, entropy, platform context, network I/O. Platform implementations: `platform/posix/`, `platform/esp32/`.
Core client must not include ESP-IDF/POSIX-specific behaviour directly.
Platform context is caller/fixed-storage oriented; do not replace with implicit heap state.
ESP32 Wi-Fi convenience layer `platform/esp32/aether_esp32_wifi.{h,c}` is optional and NOT part of the generic `aether.h` API.

Crypto registry
---------------
`include/aether_crypto_registry.h` + `src/aether_crypto_registry.c`: explicit fixed-size registry (`AETHER_MAX_CRYPTO_PROVIDERS=8`), no heap, no constructor attributes, idempotent by `crypto_lib`. Providers register their vtable/ctx; the client resolves the provider from `config.crypto_lib` when `config.crypto == NULL`.
Wire-level provider resolution in `parse_signed_key` uses `key_type` (asymmetric public key type) and, after reading the body, `sign_type`. `crypto_lib` itself is NOT transmitted on the wire.
Crypto is a significant part of generic object size but object size is not linked MCU footprint. Do not duplicate cryptographic primitives inside generated protocol code. Key serialization/transport lives in protocol code; crypto operations stay behind the crypto/backend boundary.

LAN direct delivery
-------------------
`include/aether_lan.h` + `src/aether_lan.c` + `src/aether_lan_codec.c` implement LAN discovery and direct message delivery as an ordinary caller-owned component driven by `aether_work()`. No heap; all storage caller-owned; no blocking I/O in the component.
Two independent concerns live behind one `aether_lan_t`:
- Discovery: periodic multicast beacons carry UID, certificate fingerprint, direct port. Unauthenticated; only moves a peer EMPTY -> DISCOVERED.
- Direct transport: mutual authentication with Noise XX (`hydro_kx_xx_*`), identity certificates and encrypted session. Only this path moves a peer to VERIFIED; only VERIFIED peers are eligible for direct delivery.
Peer state machine: `EMPTY -> DISCOVERED -> VERIFYING -> VERIFIED`, with explicit TTL expiry back to EMPTY. Session/wire details are in the header (`AETHER_LAN_PEER_CERT_BYTES=113`, `AETHER_LAN_AUTHORITY_CERT_BYTES=134`, handshake scratch, packet sizes). Do not duplicate wire tables here; consult the header and `src/aether_lan.c`.
`aether_lan_delivery_try` is the delivery-provider entry point (provider contract: transport-agnostic try callback returning an attempt result). Direct messages are dispatched via `aether_dispatch_message_internal`.
Transport-independent parts (UID, peer identity certificate, Noise XX, session keys, replay window) are designed so future LoRa/BLE/mesh components reuse the same identity model with different endpoints/framing.

Component vs provider abstractions
----------------------------------
The component registry (`aether_component_t`) and any delivery-provider abstraction are different concepts. Do not conflate them: components are periodic work sources; delivery providers are route candidates for one logical send attempt. A delivery/outbox abstraction is a separate concern and must not be smuggled into the component registry as a routing policy.

Send/future architecture
------------------------
`include/aether_send_future.h` + `src/aether_send_future.c`: optional asynchronous send tracking with explicit result/request identifiers and completion ownership. Fire-and-forget paths and result-waiting paths are both supported. Do not allocate a future per request on the heap. This is per-future caller-driven, not a global periodic subsystem.

Wire runtime and integer encoding
---------------------------------
Shared serialization primitives: `include/aether_meta_runtime.h`, `src/aether_meta_runtime.c`.
Writers are out-of-line shared functions taking (dest, capacity, cursor, value) and returning `aether_status_t`; no heap. Out-of-line is intentional because production generated code has many call sites and sharing reduces linked flash.
Readers are handwritten `static inline` in `aether_meta_runtime.h`; deliberate. Do not move readers back to per-generated-file copy/paste helpers. Do not force `always_inline` without measuring.
Wire compatibility > C-native representation:
- integer primitives use explicit little-endian wire order
- UUID serialization preserves the Aether UUID wire representation (MSB/LSB halves bytewise); never `memcpy` a host struct
- variable-length byte/string data is length-prefixed through the Aether pack encoding
- never serialize C struct memory directly
Intpack: Aether's compact integer packing. Do not substitute LEB128, protobuf varint, or platform-native encoding. Encode/decode changes require exact boundary-value tests.
Tiered compact integers (PackInt) are centralized in the handwritten runtime (`aether_meta_write_tiered_int` / `aether_meta_read_tiered_int`); generator integration emits constant config and calls these shared helpers. Never emit per-type tiered-int codecs.

Data I/O layer
--------------
`include/aether_dataio.h` + `src/aether_dataio.c` provide the Java-compatible `DataIn`/`DataOut` byte reader/writer used by generated peer protocol code, including canonical Float/Double NaN handling and `SerializationPackNumber`-equivalent sync and streaming pack APIs. Dynamic-array decode receives a caller-provided scratch allocator (`scratch_ctx`, `scratch_alloc`); there is no internal heap.

Peer frame / peer identity
--------------------------
`include/aether_peer.h`, `src/aether_peer_frame.c`, `src/aether_peer_uap.c`, `src/aether_peer_identity.c`, `src/aether_peer_identity_verify.c`. These implement PeerFrame/PeerHello/peer UAP and identity verification on top of the generated PeerApi bindings and `aether_dataio`.
`aether_peer.h` is a distinct concept from `aether_messages.h`'s `aether_peer_t` messaging channel. Do not confuse peer protocol framing with the messaging peer object.
Peer protocol code depends on generated `peer_api_*` bindings and on `aether_dataio.h`; keep this layering intact.

Directory naming warning
------------------------
`src/generated/` is a MIXED-PURPOSE directory for historical reasons. It contains two categories that must not be confused:
1. Direct ADSL compiler output (regenerated from ADSL; do not hand-edit as the primary fix): `client_server_*`, `peer_api_*`, `peer_lan_api_*`, and the aggregate `aether_api.*`.
2. Maintained production registration adapters/build helpers, not emitted by the current emitter: `aether_reg_global.c/.h`, `aether_reg_root_enter.c/.h`, `aether_reg_root_key.c/.h`, `aether_reg_unsafe_local.c/.h`, `aether_reg_safe.c/.h`. Treat them as maintained source unless a dedicated generator is introduced.
Do not infer edit policy from the directory name alone.

Generated binding policy
------------------------
Rule: DO NOT hand-edit `client_server_*`, `peer_api_*`, `peer_lan_api_*`, or aggregate `aether_api.*` as the primary fix.
If direct generated output is wrong:
1. change `tools/aether-protocol-c/src/emitter.c` or parser/model code
2. add/update a focused generator fixture/test
3. rebuild the generator
4. regenerate production output
5. run both generator and client tests
Generated production bindings are committed so consumers do not need the generator at runtime/build time.
Current generator CLI is unified project mode: `aether-adslc --input <adsl files...> <output-dir>`. The older per-mode flags (`--api`, `--method`, `--local-api`, `--response-method`, `-I`) are removed. Standalone modes are removed. The output is a single aggregate `aether_api.h/.c` from the whole input set.
ADSL `abbr` = abbreviated basename of the declaring ADSL file and prefixes all symbols from that file. Include resolution is by basename (no path/extension). Real conflicts are only on `abbr + type/API name` with different content, not on raw basename collisions.

C ADSL generator
----------------
Generator root: `tools/aether-protocol-c/`.
Important files:
- `include/adslc.h` — generator API/model-facing declarations
- `src/adsl.c` — ADSL parsing/model/include handling
- `src/emitter.c` — C type/API/local/stream emission
- `src/main.c` — `aether-adslc` CLI
- `tests/fixtures/` — small schemas for focused features
- `tests/test_generated_*.c` — generated wire/API regression tests
- `README.md` — public ADSL-to-C usage contract
Emitter responsibilities: C type generation, API remote-call generation, local dispatcher generation, stream-builder generation, arrays (static and dynamic), enums, nullable/collapsible fields, hierarchy/polymorphic references, intpack, UUID, reusable serializers where profitable, ADSL origin comments on generated declarations.
Recursive structs: nullable/dynamic-array recursive edges are supported with ordinary nullable-mask wire semantics; generated named codecs use hidden depth-aware `*_impl` helpers with `AETHER_META_MAX_RECURSION_DEPTH` (default 32, public ABI unchanged). Non-nullable inline layout cycles are rejected because no finite C `sizeof(T)` exists.
Collapsible METHOD (`~`) is frozen at the current minimal exact subset (noheap caller-owned typed entry storage, shared caller-owned FIFO queue, supported key shapes only). Production schemas do not currently use it; exotic key shapes are rejected rather than approximated. Do not expand without a real schema need.
Anonymous ADSL wire-visible types are not supported by policy (schema/API stability). Production anonymous returns were migrated to explicit named types. The C parser must reject anonymous params/returns/throws with a clear diagnostic, not synthesize names.
Named constants are not supported and are out of scope.

Generated-code navigation and origins
-------------------------------------
Generated declarations carry physical ADSL origin comments of the form `/* ADSL: <path>:<line> types.<Type> */` and `/* ADSL: <path>:<line> api.<Owner>.methods.<Method> */`. This covers normal remote methods, stream-builder declarations/definitions, local callback/dispatch paths, and response headers.

Polymorphic / hierarchy types
-----------------------------
ADSL inheritance/hierarchy values use generated reference/tagged-union style C types.
Selective sharing rule (measurement-driven):
- polymorphic hierarchy parameters use reusable generated serializers in `<base>_types.c`
- ordinary single-use concrete structs are currently serialized inline at API call sites
- concrete serializers can still be generated in types files and removed by linker GC when unused
Do not blindly convert every concrete struct call site to an out-of-line serializer. A measured experiment increased firmware size for single-use `Cloud`.

Linker garbage collection
-------------------------
The design assumes `-ffunction-sections -fdata-sections` + linker section GC. Therefore:
- object size of a `*_types.c.o` is NOT firmware cost
- number of generated functions is NOT firmware cost
- linked ELF/firmware measurements are authoritative
Always distinguish source size, object/archive size, linked ELF text/data/bss, and final firmware image size.

No-heap rule
------------
The runtime must remain usable without heap allocation.
Preferred patterns: caller-owned structs, caller-owned buffers, fixed-size arrays bounded by protocol/config, views (`pointer + length`), explicit storage passed into response decoding, stack-local bounded temporaries.
Do not introduce malloc/calloc/realloc/free into the core client or generated protocol runtime without an explicit architectural decision. Dynamic-array decode uses a caller-provided scratch allocator, not heap.

ESP32 footprint harness
-----------------------
Size harness: `esp32-size/`. Authoritative environment: `esp32-port`.
The harness compiles production client pieces through small wrapper translation units so PlatformIO/ESP-IDF measures linked footprint. Do not interpret an individual wrapper `.o` size as final flash usage.
ESP32-C3 physical echo example lives under `examples/echo/`; thermometer example under `examples/thermometer/`. Both drive the client with `aether_work()`.
ESP32 build-time provisioning uses CMake helpers `cmake/aether_uuid.cmake` and `cmake/aether_hex.cmake`: `aether_define_uuid(target symbol "canonical-uuid")` and `aether_define_hex_bytes(target symbol byte_count "hex")` generate compile-time constant headers. Device code never parses UUID/hex text at runtime. The helpers are NOT secure storage: values remain plaintext in generated headers and firmware.

Production regeneration
-----------------------
Unified project mode: `aether-adslc --input <ADSL files...> <output-dir>` regenerates the aggregate `aether_api.h/.c` from all production schemas. All `client_server_*`, `peer_api_*`, `peer_lan_api_*` outputs are produced from the same input set through the aggregate emitter. Inspect the current CMake/source names before regenerating; do not guess output base names or reintroduce per-mode flags.

Repository hygiene
------------------
Do not commit generator build trees (`tools/aether-protocol-c/build*/`). Do commit generator source, fixtures/tests, direct production ADSL bindings under `src/generated/`, maintained registration adapters currently colocated there, runtime source/headers, and intentionally maintained ESP32 size harness sources. `aiedit_context.yaml` is tooling context and should not be included in a feature commit unless the task explicitly changes repository tooling.
