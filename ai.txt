[Public API architecture correction]
The high-level API must not wait for a hardcoded P256 production root key.
Generic aether.h/aether.c should depend on a platform-provider boundary. A concrete platform adapter owns transport, persistence, crypto, PoW, trust roots, DNS and monotonic time.
This allows the application surface to remain:
  aether_t client;
  aether_init(&client, on_message, user);
  aether_start(&client);
  aether_send(&client, destination, data, size);
with optional stop/poll/uid/is_ready and advanced config.
The monolithic src/aether_client.c remains unchanged.
ESP32 will later provide the concrete default provider; host tests can provide a test provider.

[FINAL public/platform API boundary]
Do not split src/aether_client.c.

Application-facing API and platform integration are separate layers.

Application code must NOT construct aether_client_platform_t and must NOT know about sockets, DNS, clocks, crypto providers, PoW, trust roots or transport callbacks.

Application-facing aether.h should require only application-owned information:
- parent UID
- persistence load/save callbacks and their context
- message callback and application context
- optional ready/error callbacks and advanced timing/registration overrides

A ready platform port such as platform/esp32/aether_platform_esp32.c owns:
- TCP/UDP sockets and framing
- DNS resolver
- monotonic clock
- network polling/event integration
- crypto backend
- proof-of-work implementation
- trusted root signing keys
- binding transport callbacks to the core

Thus an ESP32 user should be able to use approximately:
  aether_config_t config;
  aether_config_default(&config);
  config.parent_uid = MY_PARENT;
  config.storage.load = my_flash_load;
  config.storage.save = my_flash_save;
  config.on_message = on_message;
  aether_init(&client, &config);
  aether_start(&client);

For common platforms we can ship ready integration files; only unusual/custom platforms need to implement the porting contract.

[ESP32 persistence organization decision]

Do not expose raw flash addresses/offsets in the beginner API.

Use logical Aether storage slots.

Default:
    aether_init(&client, parent_uid);
uses Aether storage slot 0.

Optional multiple independent Aether identities should use a logical slot API, likely:
    aether_init_slot(&client, parent_uid, slot);
unless inspection shows state is first loaded only at start, in which case a pre-start setter may be cleaner.

ESP32 implementation should map Aether slots to its own NVS namespace/keys, e.g. namespace "aether", keys "state0", "state1", etc.

Application-owned persistent data is NOT stored through Aether. Arduino/ESP32 application code continues to use normal Preferences/NVS with its own namespace such as "myapp". Thus Aether state and application state coexist safely without exposing physical flash layout.

Reasons:
- no raw offset collisions;
- NVS provides wear levelling and safer key/value persistence;
- multiple Aether identities remain possible;
- beginner API stays minimal;
- Aether does not become an unrelated generic storage framework.

[Final storage API shape]

Persistent state is loaded only when the client is started, so storage selection can be fixed during client initialization.

Beginner API:

    aether_init(&client, parent_uid);

This always uses logical Aether storage slot 0.

Optional advanced-but-still-simple variant:

    aether_init_slot(
        &client,
        parent_uid,
        1);

This selects another independent Aether identity/state.

The slot is NOT a raw flash address and must never be interpreted by application code as an offset.

Platform mapping examples:

ESP32:
    NVS namespace: "aether"
    slot 0 -> key "state0"
    slot 1 -> key "state1"

Other MCU:
    platform implementation may map the logical slot to EEPROM pages,
    flash partitions, filesystem files, etc.

Application persistent data is independent:

    Arduino Preferences preferences;
    preferences.begin("myapp", false);

or equivalent ESP-IDF NVS calls.

Thus both Aether and the application can share physical flash safely while using separate logical namespaces.

Important safety rule for ESP32 implementation:
Aether may initialize NVS if necessary but must NEVER erase the entire NVS partition automatically, because that could destroy application/WiFi/user data.

[Storage slots verification]

The selected design is intentionally simple:

Normal application:
    aether_init(&client, parent_uid);

This selects logical Aether storage slot 0 automatically.

Only applications that need another independent Aether identity use:
    aether_init_slot(&other, parent_uid, 1);

On ESP32 the ready platform integration owns persistence:
    namespace "aether"
    key "state<slot>"

Application-owned persistent data remains completely independent and uses the normal Arduino Preferences / ESP-IDF NVS API with another namespace.

No physical flash addresses are exposed.
No application flash callbacks are required by the beginner API.
No whole-NVS erase is performed by Aether.
The existing serialized Aether state format and protocol core are unchanged.
