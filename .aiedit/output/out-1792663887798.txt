<h3>Анализ stream-кода в emitter.c</h3>

<p>Фрагменты выведены выше в ответе на предыдущую команду view (строки 3987-4195, 4196-4240, 4241-4300, 4346-4582, 4583-4636, 4637-4699, 4703-4760). Ниже — детальный разбор каждой функции и сравнение с генерацией обычных методов.</p>

<h4>1. <code>emit_stream_builder_declarations_for_api_ctx</code> (3987-4195)</h4>
<p><b>Что делает:</b> для заданного stream (через stream_abbr/stream_name) и привязанного API генерирует <b>объявления</b> (прототипы) всех методов этого API как билдеров stream. Для каждого effective-метода API создаётся прототип:</p>
<pre>aether_status_t {stream_c_name}_{api_name}_{method_name}(
    {stream_c_name}_t *builder_stream
    [, {api_abbr}_{api_name}_{method_name}_context_t *collapse]  // если collapsible
    [, params...]);
</pre>
<p>Для collapsible-методов дополнительно генерируется прототип <code>..._flush</code>.</p>

<p><b>Создаваемые структуры:</b> только прототипы, никаких структур. Имя stream-типа — <code>{stream_abbr}_{stream_name}_t</code> (например <code>csa_login_stream_t</code>).</p>

<h4>2. <code>emit_stream_builder_declarations_ctx</code> (4196-4240) и <code>emit_all_stream_builder_declarations_ctx</code> (4241-4300)</h4>
<p><b><code>emit_stream_builder_declarations_ctx</code>:</b> диспетчер для конкретного stream-типа: вызывает <code>..._for_api_ctx</code> для основного <code>stream->api</code> и для всех <code>stream->apis[i].api</code>.</p>
<p><b><code>emit_all_stream_builder_declarations_ctx</code>:</b> перебирает все типы с <code>type->stream != NULL</code> и все API-методы с параметрами-стримами, для каждого вычисляет prefix через <code>stream_effective_prefix_ctx</code> и вызывает <code>emit_stream_builder_declarations_ctx</code>.</p>

<h4>3. <code>emit_stream_builder_definitions_for_api_ctx</code> (4346-4582)</h4>
<p><b>Что делает:</b> генерирует <b>определения</b> функций-билдеров для всех методов API.</p>
<ul>
<li>Для <b>не-collapsible</b> методов генерируется функция вида:
<pre>aether_status_t {stream}_{api}_{method}({stream}_t *builder_stream, params...) {
    // валидация
    // remaining = capacity - length
    // {abbr}_stream_commit_t commit = { &builder_stream->length, remaining };
    // aether_data_out_t out;
    // aether_data_out_init(&out, builder_stream->data + builder_stream->length, remaining);
    // {abbr}_{api}_remote_t remote = { &commit, {abbr}_stream_commit, &out };
    // return {abbr}_{api}_{method}(&remote, params...);
}
</pre>
</li>
<li>Для <b>collapsible</b> — аналогичная обёртка, но первым аргументом передаётся <code>collapse</code>, а также отдельная функция <code>..._flush</code>.</li>
</ul>

<p><b>Инициализация remote:</b></p>
<pre>{abbr}_{api}_remote_t remote = {
    &commit,
    {abbr}_stream_commit,
    &out
};</pre>
<p>Три поля в фигурных скобках — это агрегатная инициализация структуры <code>remote_t</code>. Если посмотреть на определение <code>remote_t</code> из обычных методов (строка 5736):</p>
<pre>typedef struct {
    void *send_ctx;
    {abbr}_send_fn send;
    aether_data_out_t *out;
} {abbr}_{api}_remote_t;</pre>
<p>Значит, stream-код инициализирует поля так: <code>send_ctx = &commit</code>, <code>send = {abbr}_stream_commit</code>, <code>out = &out</code>. Это корректно соответствует трём полям структуры.</p>

<p><b>Использование <code>aether_data_out_t</code>:</b> да, в stream-генераторе создаётся локальная переменная <code>aether_data_out_t out</code>, инициализируется через <code>aether_data_out_init</code> на буфер билдера, и указатель на неё кладётся в remote как поле <code>out</code>.</p>

<h4>4. <code>emit_stream_builder_definitions_ctx</code> (4583-4636) и <code>emit_all_stream_builder_definitions_ctx</code> (4703-4760)</h4>
<p>Аналогично декларациям: первый диспетчер, второй — перебор всех типов и вызов сначала <code>emit_stream_commit_once_ctx</code> для каждого префикса, затем <code>emit_stream_builder_definitions_ctx</code>.</p>

<h4>5. <code>emit_stream_commit_once_ctx</code> (4637-4699)</h4>
<p>Генерирует раз в каждом модуле (по префиксу):</p>
<ul>
<li>структуру <code>{abbr}_stream_commit_t</code>:
<pre>typedef struct {
    size_t *length;
    size_t remaining;
} {abbr}_stream_commit_t;</pre>
</li>
<li>static-функцию <code>{abbr}_stream_commit(void *ctx, const uint8_t *data, size_t length)</code>, которая увеличивает <code>*length</code> на <code>length</code> (проверяя overflow). Это callback для <code>send</code> в remote.</li>
</ul>

<h4>Сравнение с генерацией обычных методов</h4>
<p>Обычные методы (в <code>emit_api_source_ctx</code>, строки ~5900-5970) работают так:</p>
<ul>
<li><code>remote_t</code> создаётся пользователем (передаётся как первый аргумент <code>api</code>).</li>
<li>Метод вызывает <code>aether_data_out_write_byte(out, method_id)</code>, затем сериализует параметры через <code>emit_serialize_param_ctx</code>, и в конце вызывает <code>api->send</code> с <code>send_ctx</code> и буфером.</li>
<li><code>out</code> уже существует в <code>api->out</code> — он выделен и передан пользователем.</li>
</ul>
<p>Stream-генератор создаёт <b>обёртки</b>, которые строят <code>remote_t</code> самостоятельно на стеке, заполняя его через <code>stream_commit</code> callback и локальный <code>aether_data_out_t</code>, указывающий на буфер билдера. После вызова обычного метода данные переписываются в этот буфер, а <code>commit</code> обновляет <code>length</code>.</p>

<h4>Устаревшее / несоответствия DataInOut подходу</h4>
<ul>
<li><b>Устаревшая агрегатная инициализация:</b> используется неименованная инициализация <code>remote = { &commit, stream_commit, &out }</code>. Это хрупко — добавление нового поля в <code>remote_t</code> сломает компиляцию. Лучше использовать designated initializers (C99): <code>.send_ctx = &commit, .send = stream_commit, .out = &out</code>.</li>
<li><b>Дублирование логики валидации</b> в каждой обёртке — можно вынести в общий helper.</li>
<li><b>Несоответствие naming:</b> stream-функции называются <code>{stream_name}_{api_name}_{method}</code>, но структура remote имеет префикс <code>{api_abbr}_{api_name}_remote_t</code>. Отсутствует <code>stream_name</code> в remote — это может привести к путанице.</li>
<li><b>Косметика:</b> в коллапсируемом варианте есть лишняя запятая в fprintf (строка 4433 <code>"         ") {\n\n"</code> — видимо, опечатка, должно быть <code>") {\n\n"</code>).</li>
<li><b>Повторное использование DataInOut:</b> подход уже использует <code>aether_data_out_t</code> (это хорошо). Однако обычные методы пишут байт method-id первым, а stream-обёртки просто вызывают обычный метод, который сам это сделает — так что семантика сохраняется.</li>
</ul>

<p><b>Итог:</b> stream-код уже согласован с DataInOut (использует <code>aether_data_out_t</code>), но стиль инициализации remote стоит привести к современному C99 с designated initializers, а также вынести общую логику создания commit/remote в helper, чтобы избежать дублирования.</p>
